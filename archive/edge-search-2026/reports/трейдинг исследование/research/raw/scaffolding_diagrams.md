## Схема 1. Референсная архитектура квант-платформы (сквозной поток)

```
┌───────────────────────────────────────────────────────────────────────────────┐
│ СЛОЙ 0. ИСТОЧНИКИ ДАННЫХ (Market Data Sources)                                │
│  Биржевой multicast (ITCH/MDP)  │ Vendor API (Databento/Polygon) │ WS крипто  │
│  Reference data (инструменты, корп. действия) │ Альтернативные данные         │
└────────────────────────────┬──────────────────────────────────────────────────┘
                             │  сырые пакеты, нормализация, штампы времени
                             ▼
┌───────────────────────────────────────────────────────────────────────────────┐
│ СЛОЙ 1. ПРИЁМ И НОРМАЛИЗАЦИЯ (Ingestion / Feed Handler)                       │
│  • Feed handler на C++/Rust: декодирование бинарного протокола                │
│  • Единая внутренняя модель события (tick / quote / L2 delta / L3 order)       │
│  • ДВА штампа времени: exchange_ts и local_ts → замер шумов линии             │
│  • Sequence gap detection → запрос снапшота / переподключение                  │
└────────────────┬──────────────────────────────────────┬───────────────────────┘
                 │ горячий путь (hot path)              │ холодный путь
                 │ in-memory, lock-free SPSC ring       │ архивация
                 ▼                                      ▼
┌──────────────────────────────────┐   ┌────────────────────────────────────────┐
│ СЛОЙ 2A. РЕАЛЬНОЕ ВРЕМЯ          │   │ СЛОЙ 2B. ХРАНИЛИЩЕ (Data Lake)         │
│  • Book builder (L2/L3)          │   │  Parquet/Arrow + ArcticDB/ClickHouse   │
│  • Feature engine (OBI, VPIN,    │   │  Партиционирование: дата × инструмент  │
│    micro-price, imbalance)       │   │  Контроль качества: гэпы, пересечения  │
│  • Strategy runtime              │   │    bid>ask, всплески, дубликаты        │
└────────────┬─────────────────────┘   └──────────────┬─────────────────────────┘
             │ намерение (order intent)               │ те же данные, тот же код
             ▼                                        ▼
┌──────────────────────────────────┐   ┌────────────────────────────────────────┐
│ СЛОЙ 3. PRE-TRADE РИСК           │   │ СЛОЙ 4. ИССЛЕДОВАНИЕ (Research)        │
│  (обязательный, синхронный)      │   │  • Backtest engine (event-driven)      │
│  • Max order value / size        │   │  • Метки: triple-barrier, meta-label   │
│  • Price collar (± % от mid)     │   │  • Валидация: purged/combinatorial CV  │
│  • Max position / max gross      │   │  • Отбор: DSR, PBO, White RC, SPA      │
│  • Rate limit / message throttle │   │  • Модель издержек = продакшн-модель   │
│  • Self-trade prevention         │   └──────────────┬─────────────────────────┘
│  • Kill switch (аппаратный)      │                  │ параметры стратегии
└────────────┬─────────────────────┘◄─────────────────┘  (одна кодовая база!)
             │ валидированный ордер
             ▼
┌───────────────────────────────────────────────────────────────────────────────┐
│ СЛОЙ 5. ИСПОЛНЕНИЕ (Execution / OMS-EMS)                                      │
│  Smart Order Router → алгоритмы (TWAP/VWAP/POV/IS/Iceberg) → шлюз (FIX/бинар) │
│  Машина состояний ордера: NEW→ACK→PARTIAL→FILLED/CANCELED/REJECTED            │
│  Идемпотентность: client_order_id, восстановление состояния после рестарта    │
└────────────┬──────────────────────────────────────────────────────────────────┘
             │ исполнения (fills)
             ▼
┌───────────────────────────────────────────────────────────────────────────────┐
│ СЛОЙ 6. POST-TRADE: позиции, P&L, TCA, сверка (reconciliation) с брокером     │
│ СЛОЙ 7. НАБЛЮДАЕМОСТЬ: метрики P50/P99/P99.9 латентности, алерты, журнал      │
└───────────────────────────────────────────────────────────────────────────────┘
```

**Ключевой архитектурный принцип:** слои 2A и 4 обязаны использовать **один и тот же код признаков и одну и ту же модель издержек**. Расхождение между исследовательским и боевым контуром (research-live parity) — источник дефекта №1 в квант-системах: стратегия «работает» в бэктесте и теряет деньги в бою не потому, что рынок изменился, а потому что это буквально две разные стратегии.

## Схема 2. Бюджет задержки (latency budget), tick-to-trade

```
Событие на бирже ──┐
                   │  [1] Сеть биржа→ваш NIC
                   │      колокация, оптоволокно:      ~ 1–10 мкс
                   │      кросс-коннект в том же ЦОД
                   │      удалённо через интернет:     ~ 1–100 мс   ◄── розница
                   ▼
              Приём пакета
                   │  [2] Сетевой стек
                   │      kernel bypass (ef_vi/DPDK):  ~ 1–3 мкс
                   │      обычный сокет + epoll:       ~ 10–50 мкс
                   │      FPGA (парсинг на кристалле): ~ 50–300 нс
                   ▼
              Декодирование и обновление книги
                   │  [3] C++/Rust, прогретый кэш:     ~ 0.5–5 мкс
                   │      Python (чистый):             ~ 50–500 мкс
                   ▼
              Расчёт сигнала и решение
                   │  [4] линейная модель / пороги:    ~ 0.1–2 мкс
                   │      дерево/GBM (скомпилировано): ~ 1–20 мкс
                   │      нейросеть на GPU:            ~ 100 мкс – 5 мс
                   ▼
              Pre-trade риск-проверки
                   │  [5] in-line, без аллокаций:      ~ 0.2–2 мкс
                   ▼
              Отправка ордера
                   │  [6] кодирование + NIC:           ~ 1–5 мкс
                   ▼
Ордер в матчинге биржи

ИТОГ ПО КЛАССАМ:
  FPGA-стек (tier-1 HFT)        ~ 100 нс – 1 мкс     ← гонка за приоритет в очереди
  Оптимизированный C++/Rust     ~ 5–50 мкс           ← пригодно для MM на большинстве площадок
  Python + WebSocket, облако    ~ 5–200 мс           ← только MFT/дневные горизонты
  Розница через брокерский API  ~ 50–500 мс          ← только сигналы с горизонтом ≫ 1 мин
```

**Вывод для стратегии:** выбор горизонта стратегии **определяет** допустимый стек, а не наоборот. Попытка строить маркетмейкинг на Python/WebSocket — это не «медленнее», это структурно проигрышная позиция: вас систематически выбивает adverse selection, потому что вы всегда обновляете котировку последним.

                    ВЫСОКАЯ дифференцирующая ценность
                    (это ваша альфа / ваше преимущество)
                              ▲
                              │
        ┌─────────────────────┼─────────────────────┐
        │  III. ПАРТНЁРСТВО   │  IV. СТРОИТЬ САМИМ  │
        │      / ГИБРИД       │      (BUILD)        │
        │                     │                     │
        │  • Исполнение через │  • Генерация альфы  │
        │    брокерские алго  │  • Модель издержек  │
        │  • Управляемая      │  • Риск-лимиты      │

        │  • Prime brokerage  │  • Backtest-движок  │

сложность                     │                     │  сложность
воспроизв.                    │                     │  воспроизв.
        │  I. ПОКУПАТЬ        │  II. OPEN-SOURCE    │
        │     (BUY, SaaS)     │     + ФОРК          │
        │                     │                     │
        │  • Рыночные данные  │  • Торговый движок  │
        │  • Бухучёт/отчётн.  │    (Nautilus/Lean)  │

**Правило распределения:** покупайте всё, что не является вашей альфой и не влияет на неё напрямую; берите open-source там, где нужна полная прозрачность семантики исполнения; стройте сами только то, что (а) создаёт преимущество и (б) вы способны поддерживать 3+ года.

## Матрица 2 (2×2). Сегментация стратегий: горизонт × требуемая инфраструктура

```
                        ВЫСОКИЕ требования к инфраструктуре
                              ▲
        ┌─────────────────────┼─────────────────────┐
        │  Латентный арбитраж │  Маркетмейкинг      │
        │  Sharpe 5–15        │  Sharpe 3–8         │
        │  Ёмкость: низкая    │  Ёмкость: средняя   │
        │  Барьер: $10M+ CAPEX│  Барьер: высокий    │
мкс/нс ─┼─────────────────────┼─────────────────────┼─ дни/недели
        │                     │                     │
        │  Скальпинг на       │  Систематик-макро,  │
        │  сигналах книги     │  стат-арб, факторы  │
        │  Sharpe 1–3         │  Sharpe 0.7–2.0     │
        │  Ёмкость: низкая    │  Ёмкость: ВЫСОКАЯ   │
        │  Часто ловушка      │  Барьер: интеллект. │
        └─────────────────────┼─────────────────────┘
                              ▼
                        НИЗКИЕ требования к инфраструктуре
```

**Зона входа для нового игрока без капитала на инфраструктуру:** правый нижний квадрант. Там конкурируют идеями и дисциплиной валидации, а не наносекундами. Левый верхний квадрант закрыт капитальным барьером — туда не входят «с нуля».

## Схема 3. Воронка выживания стратегии (от идеи до боя)

```
  1000 идей / гипотез
        │  фильтр: экономическая логика, а не только корреляция
        ▼
  ~200 проходят первичный бэктест (in-sample Sharpe > 1)
        │  фильтр: purged/combinatorial CV, разные режимы рынка
        ▼
  ~40 выживают честную кросс-валидацию
        │  фильтр: реалистичные издержки (комиссия + спред + impact)
        ▼
  ~10 остаются прибыльными после издержек
        │  фильтр: множественное тестирование — DSR, PBO, White RC
        ▼
  ~3 проходят порог статистической значимости
        │  фильтр: paper trading / малый капитал, 3–6 мес
        ▼
  ~1 доходит до боевого размера
        │  и живёт в среднем 12–36 месяцев до затухания альфы
        ▼
  Требуется непрерывный конвейер: выбытие стратегий — норма, а не сбой
```

**Управленческий вывод:** квант-бизнес — это не «найти стратегию», а **построить фабрику**, которая непрерывно производит и отбраковывает стратегии. Единственная стратегия без конвейера — это опцион с истекающим сроком.
