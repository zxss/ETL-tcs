## 1. Профили ключевых движков

### 1.1 NautilusTrader — де-факто новый мейнстрим

**[ФАКТ]** Владелец — Nautech Systems (nautechsystems). Репозиторий создан 25.06.2018, лицензия LGPL-3.0. 29 099 ★, 3 827 форков, 195 контрибьюторов, 227 watchers. Коммитов за 12 мес — 5 430, причём вторая половина года дала 3 338 против 2 092 в первой (+60 %): проект **ускоряется**, а не стагнирует.

**[ФАКТ]** Релизная линия раздвоена: стабильный `v1.231.0` (02.08.2026, PyPI `nautilus_trader==1.231.0`, Python `>=3.12,<3.15`) и серия пререлизов `v2.0.0rc3/rc4/rc5` (21.08 / 02.09 / 15.09.2026). Rust-крейт `nautilus-core` — 0.64.0, обновлён 15.09.2026, 28 489 загрузок. MSRV Rust 1.98.1, поддержка Python 3.12–3.14.

**[ВЫВОД]** v1.x — последняя ветка с legacy-ядром на Cython; v2 — полностью Rust-native. Три rc за шесть недель означают, что переход на v2 идёт прямо сейчас. Для C-level это риск: строить прод на 1.x — значит подписаться на миграцию в ближайшие 6–12 месяцев; строить на rc — принимать нестабильность API.

**Архитектура [ФАКТ, из docs/concepts/architecture]:** domain-driven + event-driven. `NautilusKernel` оркеструет `MessageBus` (pub/sub + request/response + command), `Cache` (in-memory состояние с опциональной персистентностью), `DataEngine`, `ExecutionEngine`, `RiskEngine` (pre-trade проверки: баланс, размер, rate limit), `Portfolio`, `Trader`. **Вся ядровая логика — на одном потоке**; авторы прямо пишут, что накладные расходы на переключение контекста между потоками не окупались приростом. Сеть, логирование и персистентность — на отдельных потоках / в Tokio-рантайме, соединённых каналами с синхронным диспетчером. Дизайн «crash-only»: неустранимая ошибка убивает процесс, внешний супервизор перезапускает.

**[ФАКТ]** Три среды с одинаковым ядром: `backtest` (исторические данные + симулированное исполнение), `sandbox` (реальные данные + бумажное исполнение), `live`. Это и есть главный коммерческий аргумент проекта — паритет кода между исследованием и продом.

**[ФАКТ]** Интеграции (README, 18.09.2026): ~20 площадок и провайдеров. CEX-крипто — Binance, Coinbase, Kraken, OKX, Bybit, BitMEX; DEX — dYdX, Hyperliquid, Derive, Lighter; ставки/предсказательные рынки — Betfair, Polymarket; традиционный мультивеню — Interactive Brokers; данные — Databento, Tardis. Классы активов: крипто, FX, акции, фьючерсы, опционы, ставки.

**Моделирование исполнения [ФАКТ]:** наносекундное разрешение событий; конфигурируемые fill-модель, комиссии, задержки и модель книги; `book_type` должен соответствовать гранулярности данных (L1/L2/L3). Явно различаются trade-based исполнение (по тикам с aggressor side) и bar-based (по OHLC, с оговорёнными искажениями последовательности). Есть симуляционные модули для FX-роллования и CFD-swap. **[ВЫВОД]** Это лучшее сочетание «реализм × ширина покрытия» среди универсальных OSS-движков, но без честной очереди в книге уровня hftbacktest: Nautilus моделирует fill, а не позицию в очереди по каждому ордеру.

### 1.2 Hummingbot — маркетмейкинг с токен-governance

**[ФАКТ]** 20 048 ★, Apache-2.0, 234 контрибьютора, 1 697 коммитов за 12 мес, но динамика отрицательная (−24 % во втором полугодии). Релиз `v2.16.0` — 29.07.2026; на PyPI отдельная схема версий по дате сборки (`20260901`, загружен 05.09.2026), Python `>=3.10.12`.

**[ФАКТ]** Управляется Hummingbot Foundation. Токен HBOT используется **исключительно для governance**: держатели голосуют по Hummingbot Governance Proposals (HGP) — одобрение PR, распределение bounty на коннекторы, выборы совета. Коннекторы добавляются тремя путями: DIY через governance, bounty, спонсорство со стороны биржи. Экономическая модель — выручка от бирж, оплата поддерживающим коннекторы контрибьюторам.

**[ВЫВОД]** Это единственный в выборке проект с явной монетизацией через биржи, а не через подписку/облако. Обратная сторона: приоритет покрытия коннекторов определяется тем, кто платит, а не техническими нуждами — **[ГИПОТЕЗА]** качество коннекторов должно заметно расходиться между «спонсируемыми» и «DIY» биржами.

**[ВЫВОД]** Для бэктеста Hummingbot — слабый выбор: инструмент исторически построен вокруг live-исполнения стратегий MM и paper-trading, а не вокруг честной исторической симуляции.

### 1.3 Freqtrade — самый популярный, самый наивный

**[ФАКТ]** 54 499 ★ — максимум среди собственно движков в выборке (больше только у OpenBB, который не движок). 341 контрибьютор, 11 302 форка, 779 watchers. Ежемесячный календарный релизный цикл: `2026.6` (29.06), `2026.7` (31.07), `2026.8` (31.08.2026). GPL-3.0, Python `>=3.11`. Открытых issue всего 29 при 54k звёзд — **[ВЫВОД]** дисциплина сопровождения очень высокая.

**Моделирование исполнения [ФАКТ, docs/backtesting]:**
- входы исполняются по цене **open** (если не задана кастомная логика), выходы — по open следующей свечи;
- «все ордера исполняются по запрошенной цене **без проскальзывания**, пока цена внутри диапазона high/low свечи»;
- порядок оценки внутри свечи фиксирован: exit signal → stoploss → ROI → trailing stoploss;
- комиссия начисляется дважды (вход и выход), по умолчанию — дефолт биржи;
- торговые лимиты биржи учитываются, но исторические правила точности недоступны, поэтому на старых данных минимальный размер сделки завышается;
- митигация «слепоты внутри свечи» — флаг `--timeframe-detail` (например, 5m внутри 1h).

**[ВЫВОД]** Freqtrade честно документирует свои допущения — это его сильная сторона. Но для любой стратегии с горизонтом меньше нескольких свечей его бэктест систематически оптимистичен: нулевое проскальзывание + исполнение по open + произвольный порядок событий внутри бара дают именно ту комбинацию, которая превращает микроструктурный шум в «альфу».

### 1.4 QuantConnect LEAN — институциональная полнота на .NET

**[ФАКТ]** 21 670 ★, Apache-2.0, C#, 214 контрибьюторов. Коммитов за 12 мес всего 429 (+9 %) — на порядок меньше Nautilus. `releases/latest` отдаёт `v2.4.0.1` от **2017 года**: GitHub Releases в проекте не ведётся, версионирование идёт тегами (`v2.4.0.1`, `v2.4.0.0`, `v2.3.0.3`) и облачными деплоями. **[ВЫВОД]** По одним только Releases проект выглядит мёртвым — это ловушка при поверхностном скрининге; реальная активность есть, но она умеренная и, вероятно, сместилась в закрытую облачную часть.

**Reality Models [ФАКТ]:** LEAN выделяет отдельный слой «моделирования реальности» — brokerage model, fill model, slippage model, fee model, margin model, model ёмкости стратегии. Brokerage-модель задаёт комиссии, допустимые типы ордеров, рынки и поведение API конкретного брокера. Fill-модель для акций: покупка по best-effort ask + slippage, продажа по best-effort bid − slippage. Модели проскальзывания: `NullSlippageModel` (ноль, **дефолт** у `DefaultBrokerageModel`) и `ConstantSlippageModel` (постоянный процент). Учитываются расчётный цикл, комиссии, спред.

**[ВЫВОД]** Архитектурно это самая «правильная» декомпозиция реализма среди OSS (модель брокера отделена от модели исполнения отделена от модели издержек). Но дефолт «нулевое проскальзывание» — тот же капкан, что у Freqtrade: пользователь получает оптимистичный результат, не сделав ничего плохого.

### 1.7 CCXT — инфраструктурная монополия

**[ФАКТ]** 44 027 ★, MIT, 8 845 форков, 349 контрибьюторов, 951 watcher. **9 902 коммита за 12 мес** — максимум выборки, с ускорением (+67 %: 6 188 против 3 714). Версия 4.5.78 от 07.09.2026 (PyPI и релиз синхронны), Python `>=3.10`. Основной язык по классификации GitHub — Rust (**[ВЫВОД]** язык определяется по объёму строк сгенерированного кода; исходник — TypeScript, из которого транспилируются Python, C#, PHP, Go, Java и Rust). Заявлено >100 бирж и предсказательных рынков.

**[ВЫВОД]** CCXT — не движок, а несущая конструкция всего крипто-OSS: Freqtrade, значительная часть Hummingbot-экосистемы и почти все retail-боты стоят на нём. Это единая точка отказа всего сегмента и одновременно главный источник «серой» задержки: унификация всегда стоит нормализации и лишних аллокаций. **[ГИПОТЕЗА]** Для стратегий с горизонтом < 1 с CCXT-слой сам по себе съедает бюджет задержки, и профессиональные команды идут напрямую в нативные WS/FIX-протоколы бирж.

### 1.8 hftbacktest — единственная честная симуляция очереди, и она встала

**[ФАКТ]** nkaz001/hftbacktest: 4 720 ★, MIT, Rust + Python, 22 контрибьютора. **47 коммитов за 52 недели, из них 0 за последние 26 недель.** Последний коммит — 23.12.2025, последний Rust-релиз `rust-v0.9.4` (10.12.2025), PyPI `hftbacktest` 2.4.4 (10.12.2025), crates.io `hftbacktest` 0.9.4 (10.12.2025), 24 646 загрузок.

**[ВЫВОД]** Самый технически ценный проект сегмента находится в состоянии стагнации девять месяцев и держится на одном человеке (bus factor = 1). Это критический риск для любого, кто строит на нём процесс.

**Что он умеет [ФАКТ, docs]:**
- **Моделирование позиции в очереди (queue position)** — авторы называют это самой критичной компонентой HFT-бэктеста. Без него бэктест оптимистично предполагает мгновенное исполнение при касании цены, что радикально завышает прибыльность HFT.
- Для **L2**-данных — вероятностные модели очереди (`power_prob_queue_model`, `power_prob_queue_model3`, параметр n=3 и т. п.), оценивающие, сколько объёма перед вами уйдёт.
- Для **L3 (Market-By-Order)** — очередь не оценивается, а **выводится напрямую из данных**: `l3_fifo_queue_model()`, строгий price-time priority, исполнение в FIFO-порядке.
- **Двусторонние задержки**: `constant_latency(100_000, 100_000)` в наносекундах — отдельно задержка «до биржи» и «от биржи»; есть модели на основе реальных замеров.
- Полные тик-данные по трейдам и книге (L2 и L3), примеры для Binance/Bybit; L3 демонстрируется на CME MBO из Databento (`.dbn.zst` → конвертер, исправляющий задержки и порядок событий → сжатый `.npz`).
- Ограничение зафиксировано самими авторами: в CME-L3-примере глубина **не включает implied orders**.

**[ФАКТ]** Документация прямо показывает, что L2-модель очереди и L3-прямой учёт дают **заметно разные кривые эквити** на одних и тех же данных.

**[ВЫВОД]** Это главный методологический вывод всего стрима: разрыв между L2-оценкой и L3-истиной — не погрешность второго порядка, а величина, способная перевернуть знак результата у MM-стратегий. Все движки из таблицы, кроме hftbacktest, работают в парадигме «цена коснулась → исполнено» (иногда с процентом проскальзывания сверху), то есть систематически завышают доходность любой стратегии, живущей за счёт спреда или рибейтов.

## 2. Сравнение стеков: Rust vs C++ vs Python vs C#/JVM

### 2.1 Порядки задержек tick-to-trade **[ФАКТ, вторичные источники]**

| Стек | Tick-to-trade (критический путь) |
|---|---|
| FPGA | ~100–350 нс на «сыром» триггере; 100–500 нс с ускорением; лучшая задокументированная round-trip packet-in→packet-out ≈ 433 нс |
| Оптимизированный C++ | 1–10 мкс |
| Rust | ~98,7 % от эквивалентной C++-производительности в бенчмарках order-routing |
| Java | Ниже p50 ≈ 500 мкс опуститься «очень трудно» из-за недетерминизма; стандартные библиотеки не заботятся о выравнивании по кэш-линиям |

**[ВЫВОД]** Между FPGA и лучшим софтом — разрыв в 1,5–2 порядка. Это означает, что любая стратегия, чья альфа лежит в окне < 1 мкс, недоступна софтверному стеку в принципе, а значит недоступна и всей open-source экосистеме. OSS-движки конкурируют в окне ≥ единиц-десятков микросекунд.

**[ВЫВОД]** Разрыв Rust↔C++ (~1,3 %) на практике меньше, чем разброс от качества реализации. Выбор между ними — вопрос экосистемы и найма, а не производительности. Аргумент в пользу C++ — двадцать лет HFT-специфичных библиотек и тулчейнов (Boost, ZeroMQ, кастомные аллокаторы, интеграция с FPGA); аргумент в пользу Rust — безопасность памяти без GC и то, что крупные игроки (упоминается JPMorgan) уже начали переносить инфраструктурные компоненты.

### 2.2 GC-паузы в управляемых средах **[ФАКТ]**

- ZGC в современных JDK: паузы < 1 мс на кучах от 8 ГБ до 16 ТБ; типично 0,1–0,5 мс, всплески до 1 мс под давлением аллокаций. Начиная с JDK 24 неgenerational-режим удалён, ZGC только generational. Цена: +15–30 % памяти и +5–10 % CPU.
- Shenandoah: обычно 1–5 мс, всплески до 10 мс; заметно улучшен generational-режимом в Java 25.
- Задокументирован реальный отказ: на HFT-платформе всплеск рыночных данных породил лавину короткоживущих объектов, ZGC не справился, торговый движок **замер на 200 мс**.

**[ВЫВОД]** «Субмиллисекундный GC» — это медиана, а не хвост. Для торгового движка значим именно хвост, и он определяется скоростью аллокации, а не настройками коллектора. Отсюда индустриальная практика JVM-торговли: zero-allocation на горячем пути, off-heap буферы, объектные пулы — то есть Java, написанная как C. **[ВЫВОД]** LEAN и StockSharp на .NET наследуют тот же класс проблем; их ниша — бэктест и исполнение с горизонтом от сотен миллисекунд, а не HFT.

### 2.3 Python: где он реально узкое место **[ФАКТ]**

Python 3.14 (октябрь 2025) перевёл free-threading из «экспериментального» в «официально поддерживаемый» статус по PEP 779. GIL всё ещё присутствует в сборке по умолчанию; free-threading — отдельная сборка. Штраф на однопоточной производительности снизился до 5–10 %. Совместимость экосистемы — порядка 51 % популярных пакетов на 2026 год; NumPy 2.5 и SciPy активно адаптируются. Дорожная карта CPython: через 2–3 релиза (2026–2027) GIL управляется переменной окружения, ещё через 2–3 (2028–2030) — отключён по умолчанию.

**Критический подводный камень [ФАКТ]:** если импортируемое C-расширение не заявило поддержку free-threading, интерпретатор **молча включает GIL обратно** — потоки сериализуются без предупреждения.

**[ВЫВОД]** Для торгового стека это опаснее, чем отсутствие free-threading вообще: производительность становится функцией транзитивного графа зависимостей и может деградировать в 5–10 раз от добавления одного пакета, без единого сообщения в логе. Требуется CI-проверка, что GIL остался выключенным.

**[ВЫВОД]** Где Python не узкое место: генерация сигналов на барах/минутах; исследование и подбор параметров (вся тяжесть в NumPy/Numba/Polars, то есть в C/Rust); оркестрация и конфигурация; риск-контроль с горизонтом секунд. Где он узкое место: парсинг тиковых потоков в реальном времени, поддержание L2/L3-книги, любой цикл «событие → решение» с бюджетом < ~1 мс, и, что важнее, — **хвост задержки**, поскольку сборщик мусора CPython и аллокатор дают непредсказуемые всплески.

**[ВЫВОД]** Именно поэтому победившая архитектурная схема 2026 года — «компилируемое ядро + Python как control plane»: Nautilus (Rust+PyO3), hftbacktest (Rust+Python), vectorbt PRO (Numba + Rust-ядра через PyO3), CCXT (транспиляция из TS). Чистый Python остался у свечных retail-движков (Freqtrade, Jesse), где бюджет задержки измеряется секундами.

### 2.4 Стеки по задачам — итог **[ВЫВОД]**

- **(а) Бэктест (векторный/исследовательский):** Python + NumPy/Numba/Polars безальтернативен по скорости итерации. C++/Rust здесь проигрывают по стоимости разработки при сопоставимом результате, потому что вся арифметика и так в нативном коде.
- **(б) Событийная симуляция:** здесь Python проигрывает на порядки — миллиарды событий в цикле интерпретатора неприемлемы. Победители: Rust (Nautilus v2, hftbacktest, Barter) и C# (LEAN) как компромисс между производительностью и скоростью разработки.
- **(в) Low-latency исполнение:** C++ и Rust; JVM/.NET — только при жёсткой zero-allocation дисциплине и целевых задержках от сотен микросекунд; Python — только как control plane.

## 3. Архитектурные паттерны low-latency

**Lock-free очереди [ФАКТ].** LMAX Disruptor (18 471 ★, Apache-2.0, Java) — кольцевой буфер с sequence-счётчиками, в котором в каждый слот пишет ровно один поток, что снимает блокировки. Заявленные показатели: >6 млн операций/с на одном потоке, субмикросекундная задержка (часто < 100 нс); средняя задержка трёхстадийного пайплайна на три порядка ниже эквивалентного очередного подхода при ~8× большей пропускной способности. **[ФАКТ]** Репозиторий Disruptor: 0 коммитов за 52 недели, последний push 02.04.2025 — технология считается завершённой.

**Механическая симпатия [ФАКТ].** Термин введён авторами Disruptor. Практики: padding по кэш-линиям против false sharing, отказ от тяжёлых блокировок и CAS-контенции, проектирование структур данных под иерархию кэшей. **[ВЫВОД]** В открытых источниках NUMA-пиннинг, huge pages и изоляция ядер (`isolcpus`, `nohz_full`) упоминаются как стандартная практика, но воспроизводимых публичных бенчмарков вклада каждой меры я не нашёл — это область корпоративного знания.

**Zero-copy сериализация [ФАКТ].** У SBE, Cap'n Proto и FlatBuffers нет фазы кодирования/декодирования: байтовая последовательность в куче идентична той, что идёт по проводу. Цена — padding: фиксированной ширины целые несут нули в старших битах, что легко удваивает-утраивает размер сообщения; SBE и FlatBuffers сознательно оставляют padding ради zero-copy. Структурно: SBE — по сути C-структуры (переменная длина есть, union нет); Cap'n Proto и FlatBuffers используют offset-ы для переменной длины, union и прочих возможностей. В замерах на рыночных данных **SBE показал лучшую медиану и лучший worst-case**, но обладает ограниченным набором возможностей; Cap'n Proto теоретически очень быстр, но упирался в реализацию; FlatBuffers в основном выполнил обещание zero-copy. **[ФАКТ]** Актуальность: `simple-binary-encoding` (aeron-io) — 3 505 ★, 161 коммит за 12 мес; `capnproto` — 13 185 ★, 390 коммитов; `flatbuffers` — 26 483 ★, 167 коммитов; `aeron` — 8 871 ★, Apache-2.0, 1 051 коммит за 12 мес (самый активный из транспортов).

**[ВЫВОД]** Канонический JVM-стек «Aeron + SBE + Disruptor» остаётся живым и поддерживаемым (особенно Aeron). Для торгового движка выбор SBE логичен именно из-за worst-case: в HFT оптимизируют хвост, а не среднее, и отсутствие union — приемлемая плата за предсказуемость.

**Протоколы [ФАКТ].** FIX 4.4 — де-факто стандарт для многих институтов; 5.0 SP2 предлагается площадками параллельно с 4.4. Бинарные протоколы (ITCH, OUCH, PITCH) дают меньшую задержку, чем текстовый FIX, за счёт простого кодирования. OUCH — бинарный протокол ввода заявок Nasdaq с фиксированной раскладкой полей: кодируется и декодируется «за десятки наносекунд» записью по фиксированным байтовым смещениям. Рыночные данные раздаются мультикастом UDP; ITCH обычно идёт поверх внешнего слоя упорядочивания (MoldUDP64) без традиционной процедуры логона.

**Крипто vs традиционные рынки [ФАКТ].** В сравнительном бенчмарке REST/WebSocket/FIX на крипторынке: FIX даёт субмиллисекундные задержки (p50 0,177–0,263 мс на локальном loopback), REST — медиану 22–25 мс, WebSocket — p50 72–89 мс с большей вариативностью, но лучшей масштабируемостью. **[ВЫВОД]** Эти числа несопоставимы между собой напрямую (loopback vs сетевые замеры), но качественный порядок устойчив: WebSocket в крипте — это не «быстрый канал», а «удобный канал»; он на порядки медленнее и, главное, существенно более разбросан, чем FIX/мультикаст в традиционных рынках. **[ВЫВОД]** Отсюда следует, что перенос микроструктурной стратегии с трад-рынка в крипту меняет не только издержки, но и класс достижимых горизонтов.

**Идемпотентность и восстановление [ВЫВОД, подтверждено косвенно].** Прямых сравнительных исследований я не нашёл, но из архитектуры Nautilus видно принятое в индустрии решение: «crash-only» дизайн + конфигурируемая персистентность состояния + запрет на слепой реплей команд при восстановлении. Практический инвариант — клиентский идентификатор заявки (client order id), по которому после дисконнекта состояние сверяется с площадкой, а не восстанавливается из локального журнала. **[ГИПОТЕЗА]** Большинство retail-движков (Freqtrade, Jesse) полагаются на опрос состояния после реконнекта, а не на детерминированный реплей, что делает их уязвимыми к «фантомным» заявкам при разрыве в момент отправки.

## 4. Data layer: форматы, хранилища, объёмы

**Форматы [ФАКТ/ВЫВОД].** Базовый стек — Parquet + Arrow. Для книги заявок типичная конфигурация: Parquet со сжатием ZSTD(9), dictionary-encoding на большинстве колонок и delta-binary-packed на временных метках. Тиковые данные сжимаются исключительно хорошо: наносекундные метки растут малыми регулярными шагами, цены дрейфуют медленно, символы повторяются миллионы раз, trade id монотонны — дельта-кодирование обнажает эту структуру.

**Наблюдаемые объёмы [ФАКТ]:**
- 10 месяцев тиковых данных по 5 самым активным крипто-фьючерсным парам = **16,2 млрд строк, 76 ГиБ в сжатом виде** (~19× относительно сырых CSV). Это ~7,6 ГБ/мес на пять пар, т. е. порядка **0,25 ГБ/день на пять инструментов**.
- Архив книги Polymarket: ~31 ГБ / 94 файла на 18.04.2026, ~330 МБ на часовой файл.
- Nasdaq TotalView-ITCH: «десятки-сотни гигабайт» за один торговый день (точной цифры в открытых источниках не нашёл); для получения FPGA-фида Nasdaq требует подключения 10 или 40 Гбит/с.

**[ВЫВОД]** Порядки на одну машину: крипто-L2 по десятку пар — единицы ГБ/день сжатого Parquet; полнокнижные данные по американским акциям — два-три порядка больше. Это означает, что для крипто-исследования данные умещаются на один NVMe и не требуют распределённого хранилища, а для equities-L3 нужен либо специализированный сторедж, либо покупка доступа (Databento, Tardis) вместо собственного сбора. **[ВЫВОД]** Экономически: 76 ГиБ за 10 месяцев — это меньше доллара в месяц на object storage; **стоимость хранения не является ограничением, ограничением является пропускная способность приёма и стоимость лицензии на данные.**

**Хранилища [ФАКТ]:**
- **ArcticDB** (man-group): 2 514 ★, C++, 463 коммита за 12 мес, динамика ровная (−1 %). Построен в Man Group под фронт-офисные quant-исследования. Поддерживает и батч, и стриминг, наносекундную гранулярность, но **оптимизирован под батч-нагрузки**. Предшественник `man-group/arctic` (3 086 ★, LGPL-2.1) — в режиме поддержки, 0 коммитов за год, разработка мигрировала в ArcticDB.
- **QuestDB**: 17 328 ★, Apache-2.0, Java, 888 коммитов за 12 мес. Позиционируется как open-source-альтернатива kdb+: наносекундные метки, очень быстрый приём, SQL.
- **ClickHouse**: 49 957 ★, Apache-2.0, C++ — крупнейшая активность в выборке (счётчик `stats/participation` даёт 93 301, **[ВЫВОД]** число похоже на учёт всех веток/merge-коммитов, но порядок «доминирующая активность» верен). Есть публичные материалы самого вендора о замене HDB на ClickHouse для исторических тиков.
- **DuckDB**: 41 496 ★, MIT, 22 950 коммитов (та же оговорка). Ниша — встраиваемая аналитика поверх Parquet без сервера.
- **TimescaleDB**: 23 546 ★, 1 201 коммит — PostgreSQL-совместимость как главный аргумент.
- **kdb+/q**: **[ФАКТ]** лицензия содержит DeWitt clause — публикация результатов бенчмарков запрещена, поэтому независимых сравнений не существует. KX выпустила KDB-X Community Edition: бесплатно для личного **и коммерческого** использования, ограничения — максимум 16 ГБ RAM для q, один физический или виртуальный инстанс, суммарно до 24 CPU-ядер; общая коммерческая доступность KDB-X планировалась на начало 2026. Персональная редакция kdb+ — до двух компьютеров, до 24 ядер, только некоммерческое использование. Коммерческое лицензирование — по объёму RAM, числу ядер или числу пользователей; публичного прайса нет.

**[ВЫВОД]** DeWitt clause — не юридический курьёз, а структурный факт рынка: он делает невозможным доказательное сравнение «золотого стандарта» с открытыми альтернативами, чем и поддерживает статус-кво. Единственный публично доступный бенчмарк, включающий KDB-X, опубликован самой KX (TSBS, ноябрь 2025) — то есть заинтересованной стороной.

**[ВЫВОД]** Практическая рекомендация по слоям: Parquet+Arrow как формат обмена и архива → DuckDB для локального ad-hoc анализа → ClickHouse или QuestDB для централизованного тикового стора → ArcticDB, если исследование ведётся из pandas/Python и нужна версионность датасетов. kdb+ оправдан только там, где уже есть команда с q-компетенцией.

## 5. Практика бэктестинга: почему почти всё врёт

**Модель по умолчанию в OSS [ВЫВОД, из фактов раздела 1].** Подавляющее большинство движков реализует одну из двух схем:
1. **Свечная** (Freqtrade, Jesse, backtesting.py, backtrader): «если цена внутри диапазона свечи — ордер исполнен по запрошенной цене». Проскальзывание = 0, очередь не существует, порядок событий внутри бара задаётся эвристикой.
2. **Тиковая с фиксированным проскальзыванием** (LEAN по умолчанию, Nautilus в базовой конфигурации): исполнение по best bid/ask ± константа или процент.

**Чего в обеих нет [ВЫВОД]:**
- **Позиции в очереди.** Лимитная заявка на лучшей цене исполняется, как только цена «коснулась», хотя в реальности перед ней стоит очередь, которая может не рассосаться вовсе. Это и есть главный источник фантомной альфы у всего, что связано с пассивным исполнением, маркетмейкингом и рибейтами.
- **Реакции рынка на собственный ордер (market impact).** Ни один OSS-движник в выборке не моделирует, что ваша заявка меняет поведение остальных.
- **Честных частичных исполнений**, вытекающих из объёма, стоящего перед вами.
- **Асимметричных задержек.** Исключение — hftbacktest с раздельными задержками в обе стороны.

**Что такое реалистичный L3-бэктест [ФАКТ+ВЫВОД].** Это симуляция, где (а) вход — поток market-by-order событий, то есть каждая отдельная заявка с идентификатором, а не агрегированные уровни; (б) собственные заявки вставляются в ту же FIFO-очередь по price-time priority; (в) исполнение наступает только тогда, когда весь стоящий перед вами объём ушёл; (г) задержки «до» и «от» биржи моделируются отдельно и сдвигают момент постановки в очередь. Именно эту схему реализует hftbacktest (`l3_fifo_queue_model`), и именно она объясняет, почему L2- и L3-бэктесты одной стратегии на одних данных дают разные кривые эквити.

**Почему этого нет у остальных [ВЫВОД]:**
1. **Данные.** L3/MBO платны и объёмны (Databento CME MBO, Tardis для крипты). Открытый движок не может строить дефолтный сценарий на данных, которых у пользователя нет.
2. **Вычислительная стоимость.** L3-симуляция — это миллиарды событий; она невозможна в интерпретаторе и требует компилируемого ядра.
3. **Спрос.** Массовая аудитория OSS-движков торгует на горизонтах от минут, где очередь не определяет результат. Для них реализм очереди — чистые издержки.
4. **Экономика.** vectorbt показывает прямую монетизацию реализма: «более тяжёлая исполнительная семантика» вынесена в платную PRO-редакцию.

**Практический чек-лист для due diligence движка [ВЫВОД]:**
- Какое значение проскальзывания стоит по умолчанию? (У LEAN — `NullSlippageModel`, у Freqtrade — ноль внутри диапазона свечи.)
- Может ли движок вообще принять L3/MBO-поток?
- Моделируется ли задержка отдельно на пути «туда» и «обратно»?
- Начисляется ли комиссия дважды и учитываются ли funding-платежи по перпетуалам?
- Совпадает ли кодовый путь бэктеста и live? (Да — у Nautilus по построению; частично — у LEAN; нет — у векторных движков.)

**[ВЫВОД] Главный тезис стрима.** Open-source экосистема 2026 года решила задачу доступа (CCXT, Databento, Tardis) и задачу архитектуры (Rust-ядро + Python control plane). Она **не решила** задачу достоверности исполнения: единственный проект с честной очередью — hftbacktest — держится на одном мейнтейнере и девять месяцев не получал коммитов, а единственный универсальный движок с production-качеством — NautilusTrader — как раз проходит разрыв major-версии. Это и есть структурная уязвимость сегмента.

## Пробелы в данных

1. **Динамика звёзд за 12 месяцев — не получена.** GitHub API `stargazers` с заголовком `application/vnd.github.star+json` возвращает 404 (и с токеном, и без), поэтому восстановить отметки времени постановки звёзд не удалось. В качестве прокси использована динамика коммитов по полугодиям. Для whitepaper нужно либо star-history.com, либо GH Archive / BigQuery.
2. **ClickHouse (93 301) и DuckDB (22 950) коммитов за 52 недели** по `stats/participation` выглядят завышенными — вероятно, учитываются все ветки и merge-коммиты. Порядок «высокая активность» верен, абсолютные числа использовать в публикации нельзя без перепроверки.
3. **Точный объём Nasdaq TotalView-ITCH в ГБ/день** в открытых источниках не найден — только качественное «десятки-сотни ГБ». Нужен прямой запрос в Databento/Nasdaq или замер по одному дню `XNAS.ITCH`.
4. **Коммерческий прайс kdb+** не публикуется; DeWitt clause делает независимый бенчмарк юридически невозможным. Любое сравнение «kdb+ vs открытые» в whitepaper должно нести эту оговорку.
5. **.NET GC в контексте торговли** — цифр по паузам не нашёл (в отличие от JVM). Выводы по LEAN/StockSharp в этой части — экстраполяция с JVM, помечена как [ВЫВОД].
6. **Задержки самих OSS-движков** (Nautilus, Barter, hftbacktest) в наносекундах/микросекундах — воспроизводимых независимых замеров не найдено; есть только маркетинговые формулировки вендоров. Нужен собственный бенчмарк на одинаковом железе.
7. **Лицензии NOASSERTION** у StockSharp, ArcticDB, vectorbt, OpenBB, PyAlgoTrade, quickfix, capnproto — GitHub не распознал их как стандартные. Перед любым коммерческим использованием требуется отдельная юридическая проверка текста LICENSE (особенно StockSharp — вероятна двойная лицензия, и vectorbt — Commons Clause запрещает перепродажу).
8. **NUMA-пиннинг, huge pages, kernel bypass (DPDK/Onload)** — количественного вклада каждой меры в публичных источниках нет, только перечисление практик.
9. **Качество fill-моделей Jesse, StockSharp, Barter-rs** оценено по косвенным признакам (документация не прочитана целиком) — оценки в сводной таблице для этих трёх проектов следует считать [ГИПОТЕЗА], а не [ФАКТ].
10. **Hummingbot v2-стратегии и состояние бэктест-подсистемы** — конкретики за 2026 год в поиске не нашлось; вывод о слабости бэктеста основан на историческом позиционировании проекта.
