### 0.4. Какие стратегии сейчас торгуются

После аудита в `TRADING_STRATEGIES` осталось две: `intraday_short` и
`long_overnight`. `intraday_long` исключён (измеренного преимущества нет).

Значит, событийный фактор проверяется **на двух горизонтах**, а не «вообще»:

* `next_overnight` = `open(t+1) / close(t) − 1` — окно с закрытия до открытия;
* `next_intraday` = `close(t+1) / open(t+1) − 1` — основная сессия.

## 1. Гипотеза в проверяемой форме

Исходная формулировка — «структурированные события могут использоваться как
дополнительный информационный фактор» — не фальсифицируема. Рабочая версия:

> **H₁.** Существует хотя бы один тип раскрываемого события, для которого средняя
> избыточная (кросс-секционно демеанированная) доходность бумаги эмитента на
> горизонте `next_overnight` или `next_intraday`, при условии, что событие
> опубликовано **до момента выставления заявки**, статистически значимо отличается
> от нуля и по модулю превышает round-trip издержки 0,128 %.
>
> **H₂ (сильная, только при подтверждённой H₁).** Добавление этого фактора к
> действующему `FinalScore` повышает качество отбора на out-of-sample участках
> walk-forward реплея: Rank IC растёт не менее чем на +0,010, либо средний
> `realized_net` на сделку — не менее чем на +0,05 п.п.

H₀ по умолчанию: новости добавочной ценности не дают. Отклонение H₀ требует
доказательства; принятие H₀ — нормальный и вероятный исход работы.

## 2. Источники данных

### 2.1. Шлюз раскрытия Интерфакс — `gateway.e-disclosure.ru` (основной)

Спецификация снята с живого сервиса (`/swagger/v1/swagger.json`, OpenAPI 3.0.1) и
проверена, а не воспроизведена по памяти. API компактный — **шесть методов**:

| Метод | Назначение |
|---|---|
| `POST /api/v1/auth` | обмен логина/пароля на токен (`ApiKeyToken.expirationDate`) |
| `GET /api/v1/dictionaries/message-types` | **справочник типов существенных фактов** |
| `GET /api/v1/dictionaries/file-types` | справочник типов документов |
| `GET /api/v1/disclosure/events` | выборка событий |
| `GET /api/v1/disclosure/publicator-events` | то же для публикаций компаний-публикаторов |
| `GET /api/v1/disclosure/download/files/{uid}` | тело документа (поддерживает `Range`) |

Авторизация: заголовок `APIKey` + токен из `/auth`.

Параметры `/disclosure/events`: `entity` (`Messages` \| `Files`, обязателен), `count`,
`fromEventDate`/`toEventDate` **либо** `fromEventId`/`toEventId` (одновременно две
пары задавать нельзя), `subjectCode[]`, `type[]`.

Что даёт объект события:

```
DisclosureEvent.eventId    : "F200713P003453845"   — уникальный, монотонный
DisclosureEvent.eventDate  : "2020-07-13T18:40:06" — ДАТА И ВРЕМЯ ПО МОСКВЕ
MessageEvent.eventType     : Publish | Change | Exclude | Restore
MessageEvent.subject       : Individual | ResidentCompany | NotResidentCompany
Message.type               : MessageType {id, name}  — тип существенного факта
Message.header, .text      : заголовок и полный текст
Message.originalMessageUid : ссылка на ИСПРАВЛЯЕМОЕ сообщение
Message.agency, .publicUrl, .attachments
```

Четыре свойства этого API определяют архитектуру загрузчика:

1. **`eventId` монотонен** → инкрементальная докачка курсором `fromEventId`,
   ровно как watermark `MAX(message_id)` в старом контуре. Идемпотентность
   бесплатна.
2. **`eventDate` — по Москве и БЕЗ смещения в строке.** Наивный `datetime`,
   который обязан быть локализован в `Europe/Moscow` явно. Если его прочитать как
   UTC, все события сдвинутся на 3 часа назад — и вечерние раскрытия «переедут» в
   основную сессию. Это тихий look-ahead, который не даст ни одной ошибки в логах.
3. **`eventType ∈ {Change, Exclude, Restore}` — ретроспективные правки существуют
   и приходят потоком.** Именно тот риск, что назван в гипотезе п.5. API честно
   помечает их отдельным типом; обязанность контура — не применять их задним
   числом (§5.2).
4. **Тикера в API нет.** Субъект раскрытия — юрлицо с ИНН/ОГРН/кодом эмитента.
   Сопоставление с тикером строим сами (§6).

**Доступ:** требует договора с Интерфаксом и учётных данных. Проверить наличие
действующего доступа — задача №0 (§14).

### 2.2. RUDATA / DataHub — `dh2.efir-net.ru/v2/` (дополняющий)

Bearer-токен, REST/JSON, ~386 методов, контроллеры: `Info`, `Bond`, `NSD`,
`CorporateAction`, `RUPrice`, `MOEX`, `Archive`, `Rating`, `Emitent`, `Affiliate`,
`Risk`, `Solvency`, `Forecast`.

Целевой контроллер — `CorporateAction`: `/CorporateAction/Kinds`,
`/CorporateAction/KindGroups`, `/CorporateAction/Actions`, `/CorporateAction/Sources`,
`/CorporateAction/Fields`. Отдельно интересен `Forecast` — **консенсус аналитиков**:
это единственный доступный источник «ожидания», без которого `surprise` считать
не из чего (§3.3).

Swagger отдаёт 302 без авторизации — точные сигнатуры снять до получения
учётных данных нельзя. **Требование:** первый шаг работ с RUDATA — выгрузить
`/swagger` под реальным токеном и зафиксировать сигнатуры в коде по факту, а не по
этому документу. Прод-доступ платный, договорной.

### 2.3. Роли источников — не дублировать

| Источник | Роль | Незаменим в части |
|---|---|---|
| Шлюз e-disclosure | **поток событий** — что и когда стало публичным | точное время публикации, `eventType` правок |
| RUDATA `CorporateAction` | **справочник** — параметры действия (размер дивиденда, даты отсечки) | структурированные значения, а не текст |
| RUDATA `Forecast` | **ожидание** — консенсус | база для `surprise` |
| MOEX ISS (`/iss/securities/{t}/dividends.json`) | бесплатный запасной вариант по дивидендам | нулевая стоимость |

Примечание к ISS: с текущего хоста `iss.moex.com` недоступен (SSL_ERROR_SYSCALL),
проверить не удалось. Как запасной источник заявлен, но его работоспособность —
непроверенное допущение.

**Разделение ответственности жёсткое.** Время публикации берётся ТОЛЬКО из шлюза.
Значения корпоративного действия — ТОЛЬКО из RUDATA. Смешивать нельзя: у
справочника RUDATA нет достоверного момента, когда значение стало публичным, и
подстановка его времени — прямой путь к look-ahead.

## 3. Что делает LLM, а что не должно (оптимизация)

Гипотеза верно отвергает схему «новость → positive/negative». Но предложенная
замена частично воспроизводит ту же ошибку на другом уровне.

### 3.1. `event_type` LLM не нужен

В гипотезе: «LLM/NLP должен классифицировать». Но
`GET /api/v1/dictionaries/message-types` **возвращает готовый справочник типов
существенных фактов**, а каждое сообщение приходит с `Message.type.id`.

Классификация уже сделана — регулятором, единообразно, с 2011 года, бесплатно и
без ошибок разметки. Прогонять её через LLM — значит добавить шум к чистым данным
и заплатить за это. `event_type` = нормализованный `type.id` источника.

LLM остаётся нужен ровно там, где структуры нет: разрешение неоднозначности
эмитента в свободном тексте и извлечение числовых значений из сообщений, где они
не вынесены в атрибуты. Это дешёвый haiku на малой доле потока, а не разметка всего.

### 3.2. `direction` НЕ должен приходить из LLM — это скрытое предсказание цены

Гипотеза формулирует правило: «LLM должен классифицировать и структурировать, но
не должен напрямую предсказывать цену». Пример JSON в той же гипотезе содержит:

```json
"direction": { "RUB": -0.35, "MOEX": 0.20, "SBER": 0.15, "VTBR": 0.15 }
```

Это и есть предсказание цены — с точностью до знака и величины, выданное моделью,
у которой нет ни одного наблюдения реакции рынка. Правило и пример противоречат
друг другу.

**Решение:** `direction` — не вход контура, а **выход исследования**. Для каждого
`event_type` коэффициент реакции оценивается по истории (§8), хранится в отдельной
таблице оценок с доверительным интервалом и числом наблюдений, и применяется к
новому событию по его типу. Если по типу нет 200 наблюдений — коэффициента нет, и
событие идёт в панель без направления.

Это же снимает вопрос «как LLM узнает, что дивиденды выше консенсуса — это +0,15».
Никак. Это измеряется.

### 3.3. `surprise` = факт минус ожидание, и без ожидания его не существует

`surprise` определён только там, где есть заранее опубликованная база сравнения:

| Событие | Ожидание | Источник |
|---|---|---|
| Дивиденд | консенсус / прошлогодний / прогноз менеджмента | RUDATA `Forecast`, история `CorporateAction` |
| Отчётность | консенсус по выручке/прибыли | RUDATA `Forecast` |
| Ставка ЦБ | консенсус, форвардная кривая | внешний |
| Прочие существенные факты | **отсутствует** | — |

Для типов без ожидания `surprise = NULL`. Не 0,5, не «средняя». NULL, и признак
не участвует в модели для этих типов. Заполнение пропуска правдоподобным числом —
самый частый способ получить фактор, который «работает» на истории.

Альтернатива при отсутствии консенсуса — **прокси-неожиданность**: аномалия
частоты (событие этого типа у этого эмитента вне обычного календаря) и
доля повторов заголовка. Признаётся слабой; вводится только если по типу нет
консенсуса, и помечается флагом `surprise_is_proxy`.

### 3.4. `importance` и `confidence` — разные вещи, не смешивать

* `importance` — априорная значимость: вес эмитента, тип сообщения, наличие
  вложений, признак раскрытия по требованию регулятора. Считается формулой из
  структурных полей, не LLM.
* `confidence` — **достоверность извлечения**, а не уверенность в движении цены.
  1,0 для события с однозначным ИНН из справочника; ниже — для разрешённого
  текстом. Смешивание этих двух смыслов приводит к тому, что фильтр по confidence
  начинает молча отбирать события по ожидаемой прибыльности.

### 3.5. Итоговая экономика

| Шаг | Чем | Стоимость |
|---|---|---|
| Тип события | справочник API | 0 |
| Эмитент (структурный) | ИНН → тикер | 0 |
| Эмитент (текстовый, ~редко) | regex → haiku | копейки |
| Importance | формула | 0 |
| Surprise | факт − консенсус | 0 |
| Direction | оценка по истории | 0 |
| Confidence | правила извлечения | 0 |

LLM — не ядро контура, а обработчик исключений. Исходная схема ставила её в центр
пайплайна; это дороже и хуже.

## 4. Модель данных

Новые таблицы. DDL — в `models/news_events.py`, создание — из `database.init_db()`
**только** при `NEWS_ENABLED=1`, чтобы штатный конвейер не тащил лишнюю схему.

```sql
-- Событие как факт публикации. Одна строка = одна публикация в источнике.
CREATE TABLE news_events (
    event_id        VARCHAR(64) PRIMARY KEY,   -- eventId источника
    source          VARCHAR(24)  NOT NULL,     -- edisclosure | rudata | moex_iss
    entity          VARCHAR(16)  NOT NULL,     -- Messages | Files | CorporateAction
    event_kind      VARCHAR(16)  NOT NULL,     -- Publish | Change | Exclude | Restore
    source_type_id  INTEGER,                   -- Message.type.id
    event_type      VARCHAR(48)  NOT NULL,     -- нормализованный код (§4.1)

    published_at    TIMESTAMPTZ  NOT NULL,     -- eventDate, локализован Europe/Moscow
    ingested_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),  -- когда УЗНАЛИ МЫ

    subject_code    VARCHAR(64),               -- код эмитента у источника
    subject_inn     VARCHAR(16),
    subject_name    TEXT,

    supersedes_id   VARCHAR(64),               -- originalMessageUid
    header          TEXT,
    body            TEXT,
    public_url      TEXT,
    raw_payload     JSONB,
    CONSTRAINT ck_news_events_kind
        CHECK (event_kind IN ('Publish','Change','Exclude','Restore'))
);
CREATE INDEX idx_news_events_pub  ON news_events (published_at DESC);
CREATE INDEX idx_news_events_type ON news_events (event_type, published_at DESC);
CREATE INDEX idx_news_events_inn  ON news_events (subject_inn, published_at DESC);

-- Привязка события к торгуемым бумагам. Один эмитент → несколько тикеров.
CREATE TABLE news_event_tickers (
    event_id   VARCHAR(64) NOT NULL REFERENCES news_events(event_id) ON DELETE CASCADE,
    ticker     VARCHAR(10) NOT NULL,
    relation   VARCHAR(16) NOT NULL,   -- issuer | parent | sector | market
    confidence NUMERIC(4,3) NOT NULL,  -- достоверность ИЗВЛЕЧЕНИЯ (§3.4)
    PRIMARY KEY (event_id, ticker)
);

-- Соответствие юрлицо ↔ тикер. Заполняется вручную и версионируется.
CREATE TABLE issuer_map (
    inn         VARCHAR(16)  NOT NULL,
    ticker      VARCHAR(10)  NOT NULL,
    relation    VARCHAR(16)  NOT NULL DEFAULT 'issuer',
    valid_from  DATE         NOT NULL DEFAULT '2000-01-01',
    valid_to    DATE,
    note        TEXT,
    PRIMARY KEY (inn, ticker, valid_from)
);

-- Дневная панель признаков: то, что джойнится к сигналу.
-- cutoff_ts фиксирует, ПО СОСТОЯНИЮ НА КАКОЙ МОМЕНТ собрана строка.
CREATE TABLE news_features (
    asof_date        DATE        NOT NULL,
    ticker           VARCHAR(10) NOT NULL,
    horizon          VARCHAR(16) NOT NULL,   -- overnight | intraday
    cutoff_ts        TIMESTAMPTZ NOT NULL,
    ev_count         INTEGER     NOT NULL DEFAULT 0,
    ev_count_5d      INTEGER     NOT NULL DEFAULT 0,
    ev_importance    NUMERIC(5,4),
    ev_surprise      NUMERIC(6,4),
    surprise_is_proxy BOOLEAN    NOT NULL DEFAULT FALSE,
    ev_recency_min   INTEGER,
    top_event_type   VARCHAR(48),
    payload          JSONB,
    PRIMARY KEY (asof_date, ticker, horizon)
);

-- Оценённые коэффициенты реакции. Единственный источник direction (§3.2).
CREATE TABLE event_response (
    event_type   VARCHAR(48) NOT NULL,
    horizon      VARCHAR(16) NOT NULL,
    n_obs        INTEGER     NOT NULL,
    mean_abn_pp  NUMERIC(8,4) NOT NULL,   -- средняя избыточная доходность, п.п.
    se_pp        NUMERIC(8,4) NOT NULL,
    t_stat       NUMERIC(8,4),
    p_value      NUMERIC(8,6),
    q_value      NUMERIC(8,6),            -- BH-FDR по всем тестам прогона
    fitted_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    sample_from  DATE NOT NULL,
    sample_to    DATE NOT NULL,
    PRIMARY KEY (event_type, horizon, fitted_at)
);
```

### 4.1. Нормализованная таксономия `event_type`

Не изобретать. Отобразить `message-types` источника в укрупнённые коды и хранить
отображение как данные, а не как код:

`DIVIDEND_RECOMMENDATION`, `DIVIDEND_DECISION`, `REPORT_IFRS`, `REPORT_RAS`,
`BUYBACK`, `TENDER_OFFER`, `SHARE_ISSUE`, `RATING_ACTION`, `MGMT_CHANGE`,
`MA_DEAL`, `LEGAL_ACTION`, `REORGANISATION`, `LISTING_CHANGE`, `OTHER`.

Правило: `source_type_id` хранится **всегда**, даже когда отображается в `OTHER`.
Укрупнение — гипотеза аналитика; сырой id позволяет её пересмотреть без
перезагрузки истории.

## 5. Контроль look-ahead — центральное требование

Гипотеза перечисляет пять рисков (п.5). Ниже — как каждый закрывается конкретно в
этом проекте, а не вообще.

### 5.1. Cutoff привязывается к ФАЗЕ, а не к календарному дню

Это главное. Наивное правило «использовать события дня t для доходности t+1»
даёт нереализуемое преимущество, потому что оркестратор Этапа 2 выставляет заявки
в конкретные минуты (`STAGE2-DEMO-TZ` §5):

```
PREP      09:45   расчёт плана, заморозка
ORDER     10:05   выставление интрадей-заявок
CLEANUP   18:20   закрытие внутридневных позиций
OVERNIGHT 18:35   выставление ночных заявок
```

Основная сессия закрывается в 18:40, аукцион закрытия 18:40–18:50.

**Раскрытие, опубликованное в 18:45, попадает в цену закрытия и в ночной гэп — но
приходит на 10 минут ПОЗЖЕ момента выставления ночной заявки.** Исследование,
которое возьмёт «все события дня t», покажет по нему преимущество. Живая система
его не возьмёт никогда.

Отсюда жёсткое правило:

| Горизонт | Cutoff | Окно событий |
|---|---|---|
| `overnight` | `18:35` дня `t` | `(18:35 дня t−1 ; 18:35 дня t]` |
| `intraday` | `10:05` дня `t+1` | `(18:35 дня t ; 10:05 дня t+1]` |

Cutoff — конфигурируемая константа, **привязанная к тем же ключам конфигурации,
что и оркестратор** (`STAGE2_OVERNIGHT_TIME`, `STAGE2_ORDER_TIME`). Не константа в
исследовательском скрипте: расхождение между окном исследования и моментом заявки
обязано быть невозможным по построению.

Тест: при сдвиге `STAGE2_OVERNIGHT_TIME` на 18:50 в панели должны появиться
события, которых при 18:35 не было. Если не появились — cutoff не подключён.

### 5.2. Правки задним числом: `Change` / `Exclude` / `Restore`

Поток шлюза содержит исправления и удаления. Правило:

1. **Правка — это новое событие в своё собственное время.** `Change` пишется новой
   строкой с собственным `published_at` и `supersedes_id`. Исходная строка
   **не изменяется никогда**.
2. **Исторический расчёт использует только `event_kind='Publish'` со сроком
   `published_at <= cutoff`.** Правка, пришедшая позже, в расчёт на момент cutoff не
   входит — ровно как её не было у рынка.
3. **`Exclude` не удаляет строку.** Сообщение было публичным до момента исключения
   и влияло на цену. Ретроспективное удаление переписывает прошлое.
4. Ограничение целостности: `UPDATE` по `news_events` запрещён для всех колонок,
   кроме `raw_payload`. Проверяется тестом, не соглашением.

### 5.3. Наивное московское время

`eventDate` приходит как `"2020-07-13T18:40:06"` — без смещения, по Москве.
Единственная точка разбора:

```python
MSK = ZoneInfo("Europe/Moscow")
published_at = datetime.fromisoformat(raw).replace(tzinfo=MSK)
```

Запрещено: `pd.to_datetime(..., utc=True)`, `astimezone` до локализации,
хранение naive. Тест: событие `18:40:06` обязано лечь в БД как `15:40:06+00`.

Обоснование строгости: у проекта уже есть прецедент. В аудите ошибка сдвига на
один день (`benchmark_returns`) дала бету 0,05 для длинной книги, а разрыв данных
в 61 день породил фантомный «овернайт» +34,5 %, который давал половину прибыли
бэктеста. Ошибки выравнивания времени в этом коде не гипотетические.

### 5.4. Разрывы в котировках

Панель дневных баров содержит пропуски (FIXR: 2025-06-20 → 2025-08-20). Расчёт
реакции обязан использовать тот же предохранитель, что и реплей:
`audit/run_walkforward.py::MAX_GAP_DAYS = 5` — при разрыве больше 5 календарных
дней исход не определён, наблюдение выбывает. Переиспользовать константу
импортом, не копией.

### 5.5. Повторное использование события

Уникальность `event_id` — первичный ключ. Дедупликация по `(source, event_id)`.
Дополнительно — контроль на смысловой дубль: одно и то же сообщение может прийти
и как `Messages`, и как приложенный `Files`. Ключ схлопывания:
`(subject_inn, source_type_id, published_at, hash(header))`.

### 5.6. Честная граница возможного

**Историю нельзя сделать по-настоящему point-in-time задним числом.** У всех
загруженных строк `ingested_at` = момент выгрузки, то есть позже любой даты
исследования. Три меры защиты, и следует прямо признать их пределы:

* используем только `published_at` и только `Publish` (§5.2);
* с момента запуска живого сбора пишем реальный `ingested_at` и **измеряем
  задержку** `ingested_at − published_at`;
* исследование считается подтверждённым, только если p95 живой задержки укладывается
  в запас до cutoff. Если раскрытия доходят до нас в среднем за 40 минут, окно
  «до 18:35» на истории было фикцией.

Требование: минимум **20 торговых дней живого сбора** до финального вердикта по H₂,
чтобы распределение задержки было измерено, а не предположено.

## 6. Идентификация эмитента: ИНН → тикер

В API тикера нет — только `ResidentCompany.inn`, `.ogrn`, `.code`. В `instruments`
ИНН тоже нет (там `figi`, `uid`, `class_code`, `sector`). Мост нужно построить.

Задача разовая и небольшая (46 бумаг), но в ней четыре ловушки:

1. **Один эмитент — две бумаги.** `SNGS`/`SNGSP` — один ИНН. Событие обязано
   привязаться к обеим строками с `relation='issuer'`.
2. **Раскрывает дочерняя структура.** Существенный факт публикует юрлицо, которое
   не совпадает с эмитентом акции (`FEES`/Россети, `IRAO`, `ENPG`). Для таких —
   `relation='parent'`, и в исследовании они тестируются **отдельным срезом**:
   заранее неочевидно, что реакция такая же.
3. **Переименования и редомициляции.** `YNDX→YDEX`, `FIVE→X5`, `FIXP→FIXR`,
   `TCSG`. Отсюда `valid_from`/`valid_to` в `issuer_map` — плоский словарь
   молча потеряет историю до переезда.
4. **Иностранные эмитенты.** `NotResidentCompany` даёт LEI, а не ИНН, — отдельная
   ветка сопоставления.

Заполнение: разовый скрипт `scripts/build_issuer_map.py` — сверка названий из
`instruments.name` с субъектами шлюза, ручная проверка глазами всех 46 строк,
коммит результата как данных (`data/issuer_map.csv`).

**Гейт качества:** доля событий по бумагам вотчлиста, привязанных к тикеру,
не ниже 95 %. Ниже — панель дырявая и исследование недостоверно.

Замечание из старого контура: в `contrib/experimental_news/monitors/news_parser.py`
есть маппинг `TCSG → SBER` с комментарием «убрать если нежелательно». Такое
переносить нельзя: это подмена одного эмитента другим.

## 8. Этап 2 — событийное исследование

### 8.1. Расчёт мощности: что вообще можно проверить на этой истории

Считано на фактической панели (713 дней × 47 тикеров, 32 850 наблюдений).
Стандартное отклонение **избыточной** (кросс-секционно демеанированной) доходности:

| Горизонт | σ, п.п. |
|---|---|
| дневная close→close | 1,599 |
| **overnight** (close→open) | **0,618** |
| **intraday** (open→close) | 1,551 |

Минимально детектируемый эффект, α = 0,05 двусторонний, мощность 0,80
(MDE = 2,80·σ/√N):

| N наблюдений | overnight | intraday |
|---:|---:|---:|
| 50 | 0,245 п.п. | 0,614 п.п. |
| 100 | 0,173 | 0,434 |
| 200 | **0,122** | 0,307 |
| 400 | 0,087 | 0,217 |
| 800 | 0,061 | 0,154 |

Измеренные round-trip издержки — **0,128 %** (аудит, медиана по 46 бумагам).

Из этих трёх таблиц следуют три вывода, определяющих весь этап:

**Вывод 1. Овернайт-горизонт мощнее интрадейного в 2,5 раза.** Порог
обнаружимости при N = 200 составляет 0,122 п.п. для овернайта против 0,307 п.п.
для интрадея. При этом раскрытия по регламенту публикуются преимущественно
**после закрытия сессии** и попадают именно в ночной гэп. Событийный контур
следует нацеливать в первую очередь на `long_overnight`.

**Вывод 2. Требование N ≥ 200 на тип события — не бюрократия, а граница смысла.**
При N = 50 на овернайте различим только эффект 0,245 п.п.; всё, что слабее,
неотличимо от нуля. Ожидаемые объёмы на 2,3 года × 46 бумаг:

| Тип | Частота | Ожидаемое N | Проверяем? |
|---|---|---:|---|
| Отчётность (МСФО+РСБУ) | ~4/год/эмитент | ≈ 420 | да |
| Дивиденды (рекомендация + решение) | ~2/год/эмитент | ≈ 210 | на грани |
| Прочие существенные факты (агрегат) | десятки/год/эмитент | тысячи | да |
| Смена менеджмента, M&A, рейтинги | единицы/год | < 100 | **нет** |
| **Решения ЦБ по ставке** | 8/год | **≈ 18** | **нет** |

**Вывод 3. Общерыночные события на этой истории непроверяемы в принципе.**
Решение ЦБ затрагивает все 46 бумаг одновременно — это 18 наблюдений, а не
18 × 46 = 828. Кросс-секционная корреляция съедает независимость целиком.
MDE при N = 18 составляет ≈ 1,05 п.п. Событие, двигающее рынок меньше чем на
процент, на 2,3 годах не обнаружимо ничем.

Практическое следствие: пример из гипотезы — `CENTRAL_BANK_DECISION` с
`direction` по четырём инструментам — относится ровно к тому классу событий,
который эта история проверить не позволяет. Такие типы собираем (они пригодятся
через три года), но в исследование и в торговлю не берём. Заявлять по ним
`direction` без наблюдений — это и есть подгонка.

### 8.2. Методика

Для каждой пары (`event_type`, `horizon`):

1. Выборка: `Publish`-события с `published_at` внутри окна горизонта (§5.1),
   привязанные к тикеру с `relation='issuer'`.
2. Исход: избыточная доходность = доходность бумаги минус кросс-секционное среднее
   того же дня. Изоляция от рыночного движения без оценки беты (на 713 днях бета
   шумная, а демеанирование — не оценка).
3. Наблюдение выбывает при разрыве > `MAX_GAP_DAYS` (§5.4).
4. Статистика: среднее, SE, t. **Кластеризация ошибок по дате** — обязательна:
   события одного дня коррелированы, а обычный t их посчитает независимыми и
   завысит значимость.
5. Форма реакции: профиль по 5-минуткам для дат ≥ 2025-11-30 (там, где есть
   `market_data_5m`) — распад преимущества внутри дня. Это ~190 торговых дней;
   срез разведочный, к гейту не относится.
6. Срезы: сектор (`instruments.sector` уже заполнен), уровень `importance`,
   знак `surprise`, режим рынка (`tft_forecast/market.py`), `relation` (issuer vs parent).

### 8.3. Множественность проверок — объявляется ДО расчёта

Число тестов = типы × горизонты × срезы. **Записывается в отчёт до запуска.**
При ~14 типах × 2 горизонта × 4 среза = 112 тестов ожидаемое число ложных
«открытий» на уровне 0,05 — около шести. Без поправки исследование гарантированно
найдёт «работающий» тип события, даже если новости не значат ничего.

Обязательно:
* **BH-FDR** q < 0,10 по всему семейству тестов прогона;
* повышенный порог одиночного теста: **|t| ≥ 3,0**, не 2,0;
* устойчивость: эффект сохраняет знак на обеих половинах выборки и **после
  удаления пяти дней с наибольшим вкладом**. Последнее — прямой урок аудита:
  119 % прибыли конфигурации приходилось на 5 дней из 151.

### 8.4. Приёмка — Гейт B

| # | Критерий | Порог |
|---|---|---|
| B1 | Есть тип с достаточной выборкой | N ≥ 200 |
| B2 | Размер эффекта покрывает издержки | \|mean_abn\| ≥ 0,25 п.п. |
| B3 | Значимость с кластеризацией по дате | \|t\| ≥ 3,0 |
| B4 | Поправка на множественность | BH-FDR q < 0,10 |
| B5 | Устойчивость по половинам | знак совпадает |
| B6 | Устойчивость к выбросам | эффект жив без топ-5 дней |

**Гейт B не пройден → работы останавливаются на Этапе 1.** Контур остаётся
аналитическим источником: события собираются, доступны в дашборде как справка,
торговлю не трогают. Это штатный результат, а не провал.

## 9. Этап 3 — добавочная ценность к действующей модели

Запускается только при пройденном Гейте B.

### 9.1. Что именно сравнивается

Проверяется не «предсказывают ли новости», а **добавляют ли они сверх того, что
модель уже знает**. Действующий `FinalScore` (heuristic: 0,70·exp + 0,20·prob +
0,10·liq) даёт на реплее Rank IC = 0,0512 при t = 2,83 на 456 днях. База сравнения — он.

Протокол: тот же walk-forward, что в аудите (`audit/replay.py` —
12 мес. train → 2 мес. OOS → шаг 1 мес., 17 фолдов), с признаками новостей,
рассчитанными **строго по cutoff соответствующей фазы**.

Сравнение попарное по фолдам, а не по общему числу: 17 наблюдений разницы,
t-тест по фолдам.

### 9.2. Как встраивать — фильтром, а не слагаемым

Очевидное решение — добавить `news_score` четвёртым слагаемым в `_score_row`.
**Не рекомендуется.**

История проекта прямо против: из формулы уже удалены `rs_score`, `regime_score`,
`vol_score` и `validation_score` — их измеренный вклад был неотличим от нуля, и
их присутствие ухудшало отбор. Rank IC вырос с 0,0262 (t = 1,30) до 0,0512
(t = 2,83) **после удаления пяти компонентов**, а не после добавления новых.
Все выжившие преимущества оформлены как фильтры в
`apply_strategy_specialisation()`, а не как веса.

Рекомендуемый порядок ввода:

| Шаг | Форма | Требование |
|---|---|---|
| 1 | Бинарный **блокирующий** фильтр: не открывать позицию против свежего события подтверждённого типа | разница средних `realized_net` значима |
| 2 | Бинарный **разрешающий** фильтр: приоритет кандидатам с подтверждённым событием в свою сторону | то же |
| 3 | Слагаемое в `FinalScore` | Rank IC самого признака ≥ 0,03 при \|t\| ≥ 2,0 |

Шаг 3 — только если признак самостоятельно проходит тот же порог, по которому
отбраковывались удалённые компоненты. Иначе — остаётся фильтром.

Технически шаги 1–2 — новая функция в `combined.py` рядом с `_seller_momentum()`
и `_overnight_market_too_hot()`, вызываемая из `apply_strategy_specialisation()`
под `NEWS_SIGNAL_ENABLED`. Она обязана возвращать `None` при отсутствии данных:
принятое в проекте правило «незнание не есть отказ» (`test_squeeze_guard_ignores_missing_data`).
Сбой загрузчика новостей не должен останавливать торговлю.

### 9.3. Приёмка — Гейт C

| # | Критерий | Порог |
|---|---|---|
| C1 | Прирост Rank IC на OOS | ΔIC ≥ +0,010, t по 17 фолдам ≥ 2,0 |
| C2 | Либо прирост исхода сделки | Δ`realized_net` ≥ +0,05 п.п./сделку, \|t\| ≥ 2,0 |
| C3 | Не ломает базу | Δ не отрицательна ни в одном из двух полугодий |
| C4 | PBO (CSCV) | < 0,50 |
| C5 | Живая задержка подтверждена | p95 (`ingested_at − published_at`) укладывается в запас до cutoff, ≥ 20 торговых дней измерений |
| C6 | Число испытаний учтено | все конфигурации фильтра посчитаны в `N_TRIALS`, DSR пересчитан |

C5 и C6 — не формальность. C5 закрывает единственную дыру, которую исторический
массив закрыть не может (§5.6). C6 — потому что `audit/reaudit.py` уже ведёт
`N_TRIALS = 15`, и каждая новая проверенная конфигурация фильтра увеличивает этот
счётчик, снижая Deflated Sharpe всей системы. При текущем DSR 0,251 добавление
испытаний без прироста результата ухудшает общий вердикт.

## 10. Что этот контур делать НЕ будет

Явные ограничения, чтобы работа не расползлась:

1. **Не менять торговую стратегию и алгоритм отбора** до пройденного Гейта C.
   До этого весь код новостей — read-only относительно `combined.py` и
   `place_orders.py`.
2. **Не использовать LLM для предсказания направления или величины движения.**
   Только классификация, извлечение и разрешение неоднозначностей (§3).
3. **Не оценивать контур по прибыльности на Этапе 1.** Sharpe, CAGR и Profit
   Factor неприменимы к задаче сбора данных.
4. **Не заводить параллельную архитектуру.** HTTP — через слой `loaders/`,
   календарь — `services/calendar.py`, БД — `database.py`, конфигурация —
   `config.py`, тесты — в общий прогон.
5. **Не включать `news_sentiment` из старого контура** и не переиспользовать его
   трёхзначный сентимент.
6. **Не расширять вотчлист** ради увеличения выборки событий: универсум фиксирован
   46 бумагами, изменение универсума аннулирует сопоставимость с аудитом.

## 11. Сводный план и объём

| Этап | Содержание | Объём | Результат | Гейт |
|---|---|---|---|---|
| 0 | Учётные данные, справочники, `issuer_map` | ~150 строк + ручная приёмка | мост ИНН↔тикер | — |
| 1 | Загрузчик, нормализация, панель, тесты | ~1 470 строк | исторический массив событий | **A** |
| 2 | Событийное исследование, отчёт | ~600 строк | `NEWS-EVENT-STUDY.md`, таблица `event_response` | **B** |
| 3 | Фильтр в отборе, walk-forward сравнение | ~350 строк | вердикт по H₂ | **C** |

Этапы 2 и 3 запускаются только при пройденном предыдущем гейте. Ожидаемый исход
по опыту аудита — **остановка на Гейте B**, и к этому следует относиться как к
нормальному результату: контур останется аналитическим.

Отчёт Этапа 2 (`NEWS-EVENT-STUDY.md`) обязан содержать, по образцу
`AUDIT-PROFITABILITY-REPORT.md`: объявленное до расчёта число тестов, таблицу по
всем типам событий (включая непрошедшие), кластеризованные t-статистики, BH-FDR
q-значения и раздел «что этот результат не доказывает».

## 12. Вопросы, требующие решения до начала работ

1. **Доступ к шлюзу e-disclosure.** Есть ли действующий договор с Интерфаксом и
   учётные данные? Без них Этап 1 неисполним, а вся конструкция ТЗ повисает.
   Оценить стоимость доступа до написания кода.
2. **Доступ к RUDATA.** Нужен только для `surprise` (консенсус) и параметров
   корпоративных действий. Если доступа нет — Этап 1 исполним на одном шлюзе, но
   `surprise` для всех типов станет `NULL`, и проверять придётся только факт
   события, без его неожиданности. Это допустимо, но заметно слабее.
3. **Приоритет горизонта.** Расчёт мощности (§8.1) говорит начинать с
   `long_overnight`. Подтверждаете сужение первой итерации до овернайта, или
   считать оба горизонта сразу (дороже, слабее по мощности на интрадее)?
4. **Бюджет LLM.** При `NEWS_LLM_ENABLED=1` расход — haiku на доле потока, где
   структурного ИНН нет. Нужен потолок расхода в месяц как конфигурационный ключ.
