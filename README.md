# ETL — исторические биржевые данные (T-Invest API → PostgreSQL)

Загружает дневные свечи по тикерам **SBER, GAZP, ROSN, LKOH, GMKN, NVTK, PLZL**
за последние 24 месяца и сохраняет их в PostgreSQL.

## Структура проекта

```
ETL-tcs/
├── main.py                  # точка входа
├── config.py                # параметры из .env
├── database.py              # подключение к PG, upsert
├── loaders/
│   └── moex_loader.py       # HTTP-клиент T-Invest API
├── models/
│   └── market_data.py       # DDL таблицы и SQL-запросы
├── services/
│   └── load_history.py      # оркестрация ETL по тикерам
├── .env                     # переменные окружения (не коммитить!)
├── requirements.txt
└── README.md
```

Переменные для торгового контура и TLS (все опциональны для чистого ETL):

```env
# Боевой счёт. Захардкоженного значения в коде НЕТ: без этой переменной любая
# работа с PROD падает с ValueError("PROD_ACCOUNT_ID не задан в .env").
PROD_ACCOUNT_ID=

# Проверка TLS-сертификатов брокера. 1 (по умолчанию) — включена.
# 0 — отключить осознанно; в лог пишется "TLS verification DISABLED!".
INVEST_TLS_VERIFY=1

# Сертификат T-Invest подписан «Russian Trusted Root CA» (Минцифры), которого
# нет в дефолтном хранилище Python. Без этого бандла проверка падает
# CERTIFICATE_VERIFY_FAILED. Корень берётся с https://gu-st.ru (Госуслуги).
INVEST_CA_BUNDLE=/path/to/russian_trusted_root_ca.pem
```

## Торговые контуры (services/place_orders.py, services/cancel_orders.py)

Контур по умолчанию — **SANDBOX** (виртуальные деньги):

```bash
python3 -m services.place_orders --top-n 10          # песочница
python3 -m services.place_orders --prod --top-n 10   # БОЕВОЙ счёт, реальные деньги
```

Неинтерактивный запуск на бою (`--prod --no-confirm`, cron) дополнительно
требует `ALLOW_UNATTENDED_PROD=1` в окружении — иначе `RuntimeError`.

### Нешортабельные бумаги

По части бумаг брокер не даёт маржинальный шорт (`shortEnabledFlag=false`), и
заявка SELL без позиции по ним отклоняется. Такие сигналы отсекаются на двух
уровнях:

1. `tft_forecast/combined.py` — список `NON_SHORTABLE_TICKERS` убирает
   SHORT-строку до отбора топ-N, с записью в лог
   `[SKIP SHORT] {ticker}: шорт недоступен у брокера`. Бумага не выпадает
   целиком: LONG-кандидат по ней остаётся.
2. `services/place_orders.py` — жёсткий гард по ЖИВОМУ флагу
   `Instrument.short_enabled` из `InstrumentsService/ShareBy`. Ловит случаи,
   когда брокер снял бумагу с маржиналки, а список ещё не обновили.

Базовый список сверен с API по всем тикерам `config.TICKERS`: `AKRN`, `CBOM`,
`MVID`. Расширяется из `.env`:

```env
NON_SHORTABLE_TICKERS=AKRN CBOM MVID XXXX
```

Не путать с `TINKOFF_UNAVAILABLE_TICKERS` — там бумаги, по которым нельзя
торговать вообще (делистинг, смена ISIN), а не только шортить.

## Хранение прогнозов

Строки дневного и недельного дашбордов пишутся в таблицу `forecasts` (upsert по
`asof_date + ticker + strategy`), чтобы потом сверять прогноз с фактом. Дневные
строки идут со своей стратегией, недельный дашборд — со стратегией `weekly`.
Всё, что не влезло в колонки (рыночный контекст, метрики валидации,
ликвидность), лежит в `raw_payload JSONB`.

```env
SAVE_FORECASTS=1     # 0 — только печать дашбордов, без записи в БД
DB_POOL_MIN=1        # пул соединений PostgreSQL
DB_POOL_MAX=5        # должен быть > MAX_CONCURRENT_TICKERS
```

Прочитать сохранённое: `database.query_forecasts(asof_date, ticker=None)`.

## Статус конвейера

`main.py` ведёт учёт этапов и в конце печатает сводку:

```
Pipeline Summary:
- ETL: SUCCESS
- Index: FAILED (RuntimeError: timeout к API)
- Forecast: SUCCESS
- Place Orders: SKIPPED (отдельная команда: python3 -m services.place_orders)
```

Падение этапа из `CRITICAL_STAGES` (`etl`, `forecast`) → `sys.exit(1)`.
Остальные этапы падают «мягко»: конвейер идёт дальше, но статус виден в сводке
и в логе. Раньше любая ошибка глушилась и код возврата всегда был 0.

## Происхождение дневных баров

Колонка `market_data.source`:

| Значение | Что это |
|---|---|
| `api` | официальный дневной бар биржи (значение по умолчанию для новых вставок из брокерского API) |
| `backfill_5m` | локальная интрадей-реконструкция из 5-минуток (`services/backfill_daily.py`), когда официальный бар ещё не опубликован |
| `api_legacy` | исторические данные до развёртывания трекинга источника: происхождение достоверно неизвестно, среди них могут быть реконструированные бары |

Когда брокер публикует настоящий бар, ETL перезаписывает реконструкцию и
возвращает `source = 'api'`.

Разовая разметка исторического слоя (идемпотентна):

```bash
python3 -m scripts.mark_legacy_source --dry-run
python3 -m scripts.mark_legacy_source
```

## Торговый календарь (weekend trading)

В `market_data` есть бары за субботы и воскресенья — сессии выходного дня по
всем 47 тикерам. Средний объём в них примерно в 8 раз ниже будничного, из-за
чего ADV60 занижался на 30–50 % по ликвидным бумагам. Режим задаётся
`INCLUDE_WEEKEND_TRADING`, общий календарь живёт в `trading_calendar.py`.

| Режим | Поведение |
|---|---|
| `0` (по умолчанию) | Строгий биржевой календарь. Бары выходных отбрасываются при загрузке датасета валидации, TFT, рыночного контекста и ликвидности. Дашборды считают окно по Пн–Пт. |
| `1` | Торговля 7 дней в неделю. Бары выходных остаются, торговые дни определяются по фактическому наличию торгов в БД, а не проверкой дня недели. |

Шаг модели и окно в шапке дашборда считаются одним календарём, поэтому
расходиться не могут: `H` шагов датасета = `get_target_horizon_date(asof, H)`.
Со вторника 08.09 при `H=5` окно — `Ср 09.09 — Вт 15.09` в режиме 0 и
`Ср 09.09 — Вс 13.09` в режиме 1.

### Праздники и расписание биржи

Праздники, переносы и синхронизация с биржей — в `services/calendar.py`
(`TradingCalendar`). Источники по приоритету:

1. `InstrumentsService/TradingSchedules` по бирже MOEX — авторитетный, но узкий:
   API отдаёт только окно `[сегодня; сегодня+14]` (`from` в прошлом и `to`
   дальше 14 дней отклоняются). Горизонт `H=5` в него укладывается всегда.
   Синхронизация запускается в `main.py` отдельным шагом `Trading calendar`.
2. Встроенный оффлайн-словарь `MOEX_HOLIDAYS` / `WORKING_WEEKENDS` — fallback
   без сети, работает на любую дату.
3. Маска дней недели из режима `INCLUDE_WEEKEND_TRADING`.

**Календарь биржи — это не производственный календарь РФ.** По данным
`market_data` биржа с 2026 года торгует в большинство госпраздников
(23.02, 09.03, 01.05, 11.05, 12.06 — бары есть), закрываясь только на
новогодние даты (31.12, 01–02.01) и Рождество (07.01). Поэтому оффлайн-словарь
содержит фактические остановки торгов, сверенные с историей баров, а не список
нерабочих дней по ТК РФ: иначе окно прогноза перешагивало бы через дни, когда
биржа работает.

Даты 2027 года в словаре — экстраполяция биржевого шаблона, а не официальное
постановление (оно ещё не публиковалось); по мере приближения они вытесняются
данными из API. Список рабочих суббот требует обновления по каждому ежегодному
постановлению Правительства РФ.

При недоступности API шаг помечается `WARNING` в сводке конвейера, календарь
прозрачно откатывается на оффлайн-набор, прогон не падает.

## Тесты

Тесты написаны на stdlib `unittest` — отдельной зависимости не требуют
(`pytest` не установлен и в `requirements.txt` не входит; `tests/conftest.py`
объявляет фабрики обычными функциями, поэтому набор запускается обоими
раннерами).

```bash
python3 -m unittest discover -s tests -t .        # весь набор
python3 -m unittest tests.test_calendar -v        # торговый календарь
python3 -m unittest tests.test_risk_and_orders -v # сайзинг, цены, риск, скоринг
```

`tests/test_risk_and_orders.py` покрывает узлы, где ошибка стоит денег:
лотность и квантование (`_api_quantity`), цены входа/стопа/тейка внутри
квантильного коридора, риск-паритетное распределение бюджета и штрафы
`FinalScore` (контртренд к IMOEX, High Risk Short, Volume Climax, overnight-гэп).

## Очистка мёртвых тикеров

Делистнутые бумаги (например `FIXP` после редомициляции в `FIXR`) оставляют
замороженную историю, которая продолжает участвовать в кросс-секционных
расчётах. Скрипт переносит их в `market_data_archive` / `market_data_5m_archive`:

```bash
python3 -m scripts.cleanup_stale_tickers --dry-run     # показать кандидатов
python3 -m scripts.cleanup_stale_tickers               # архивировать
python3 -m scripts.cleanup_stale_tickers --restore FIXP  # вернуть обратно
python3 -m scripts.cleanup_stale_tickers --purge       # удалить безвозвратно
```

Кандидат — тикер, которого нет в `config.TICKERS`/`INDEX_TICKERS`/`TFT_TICKERS`/
`VALIDATION_TICKERS` и чей последний бар отстаёт от максимальной даты в БД
на `--stale-days` (по умолчанию 30).

## Схема таблицы

| Поле       | Тип            | Описание                        |
|------------|----------------|---------------------------------|
| id         | BIGSERIAL PK   | Суррогатный ключ                |
| ticker     | VARCHAR(10)     | Тикер (SBER, LKOH, ...)         |
| date       | DATE           | Дата торговой сессии            |
| open       | NUMERIC(18,4)  | Цена открытия                   |
| high       | NUMERIC(18,4)  | Максимум дня                    |
| low        | NUMERIC(18,4)  | Минимум дня                     |
| close      | NUMERIC(18,4)  | Цена закрытия                   |
| volume     | BIGINT         | Объём в лотах                   |
| created_at | TIMESTAMPTZ    | Время загрузки                  |

Уникальный ключ: `(ticker, date)` — повторные запуски безопасны (upsert).
